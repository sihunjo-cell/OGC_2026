# prob_26에서 crane 게이트가 합법 배치를 수치 오차로 거부한다 — 세 기준선에서 살아남은 마지막 미세기하 밴드

## 배경 (전부 실측)

mask 비가시 anchor 프로브([tools/diag_nestle.py](../tools/diag_nestle.py), 저장해 위에서 배치
엔진의 눈과 정밀 판정을 나란히 돌리는 오프라인 계기)가 26의 막힌 순간을 두 층으로 분해했다.
"mask가 못 본 합법 배치" 층은 N2(k32 회수)와 B20(cap32/flop2e10 재보정)으로 **배포 회수가
끝났다**(밴드 8.33 → 1.99%). 그와 별개로, **공간은 정밀 판정으로 완전히 비어 있는데 crane
게이트가 전 anchor를 전멸시키는 순간**이 남아 있다:

* 실측 사슬 — **세 기준선에서 재현**: pre-N2 7.11% → 회수+ΔF 배선 후 7.41% → **B20 이후
  5.97%**(잰 해 = 26 10.28M). 회수 레짐이 두 번 갈렸는데 층이 그대로다 = 병인이 해의 우연이
  아니라 게이트 자체에 있다.
* 26이 하필 그런 문제인 것도 독립 인증돼 있다: 용량 하한 인증서에서 26은 **하한 = 0**(용량
  100% 가정 시 2.5초 만에 최적 0) = 지각이 용량으로 전혀 설명 안 되는 **순수 모양·간섭 병인**.
  은행 26 = 11.5M(T600) → B20 후 T300 스모크 10.5M — 남은 전액이 이런 미세기하 층이다.
* 기전은 코드로 특정돼 있다: crane 판정의 ray-cast([point_in_rings](../Phase2/geometry_query.py#L93))가
  **변 접촉(면적 0 = 공식 체커 기준 합법)을 수치 불안정하게 충돌로 친다** — 2026-07-14 fuzz에서
  관측·기록된 그 현상이고, 프로브가 누적 크기를 잰 것이다.
* 같은 급("엔진의 눈이 거부한 합법 배치의 회수") 전례가 **2전 2승**이다: N2(비가시 12.55% →
  T300 부하-쌍대 −16~28%, 전40 LOO −13.0%)·B20(밴드 8.33→1.99%, 26 6/6 −5~12.6%). 이 계열의
  실측 전환율이 현 코드베이스에서 가장 높다 — 본 이슈를 확실성 1위에 두는 근거.

## 현재 문제

### 1. 보수성의 방향이 손실 쪽으로만 작동한다

게이트의 이중 보수(경계를 양쪽 모두 충돌로 침, [`_exact_gate`](../Phase2/dispatch.py#L98))는
안전을 위한 선택이지만, 안전은 최종적으로 공식 체커 인증(driver의 crane 인증 + repair 루프)이
따로 보장한다 — 게이트에서의 과잉 거부는 안전 이득 없이 배치 기회만 잃는다. 자리를 못 찾은
block은 대기하고, 대기는 곧 tardiness다.

### 2. 잔여 밴드의 나머지 성분은 비후보로 정리됐다

B20 재프로브에서 비가시 잔여는 count p50/p90 = 33/67 = **K=32 절단 바깥만** 남았는데, raw
귀속 실험에서 K64는 무효(−10.3% < cap·FLOP축 −12.5%)로 실측됐다 — K-확장은 후보가 아니다.
즉 26에서 실측 근거가 서 있는 남은 층은 crane-eaten 하나다.

## 개선 방향

### A. 게이트 거부 anchor의 공식-체커-기준 미러 재판정 (주 처방)

**어디를 바꿀까:** [`_try_nestle`](../Phase2/dispatch.py#L108)에서 space_ok 통과 후
[`_exact_gate`](../Phase2/dispatch.py#L98)가 거부한 anchor에 대한 재판정 분기. flag
`dispatch_nestle_crane_mirror`(False = off = 현행과 byte 동일).

**논리:** 거부된 (block, anchor)를 공식 체커와 같은 기준(shapely, 변 접촉 = 합법, EPS 허용)
으로 1회 재판정해 통과하면 admit. 기하 구조는 [ExactSpace](../Phase2/nestle.py#L126)가 이미
보유(suffix-union) — 확장은 ①내 EXIT 시점 stayers 검사 ②조기-퇴장 상주의 exit sweep 역방향
검사. 프로브의 exact leg가 이 판정을 이미 구현·판정-동치 검증했으므로 빌드는 이식에 가깝다.
비용은 게이트-거부 순간에만 발생, nestle FLOP 캡 지배하(신규 스캔 0) = 자기 제한. 커밋 뒤
공식 체커 인증 경로가 그대로라 feasibility 신규 위험 0.

### B. ray-cast 자체의 경계 처리 수선 (비권고)

전 경로(충돌·crane 공용)의 궤적을 한꺼번에 바꿔 검증 표면이 A(국소 재판정)보다 훨씬 크다.
A가 무효로 판정될 때만.

## 우선순위

**착수 1순위.** 근거: (1) 병인이 세 기준선에서 재현됐고 기전이 코드 한 지점으로 특정돼 있다,
(2) 판정 기준기(프로브 exact leg)가 이미 검증돼 있어 빌드가 이식이다, (3) 같은 계열 전례가
2/2로 실측 전환됐다 — 이 목록에서 근거 사슬이 가장 짧고 단단하다.

**게이트(사전등록):** off = byte 동일 + 같은 seed 결정론 → T=300 부하-쌍대 **{26} × {κ3-fd,
κ1} × 3seed** paired ≤ −3% & 부호 일관 → 캐너리 T=300 {39, 30}(nestle 수혜군 = 노출 집합) →
**발화-집합 게이트**(발화 문제 실측 + 미발화 raw 동일값 스크린 — 전40 blanket 대체, B20에서
확립한 방법론) → 크래시 프록시 3종(배선 직전) → **기전 확인 = diag_nestle 재프로브**
(crane-eaten 5.97%가 실제로 줄었는지). **Kill:** 26 2구성 전패 시 — 사인을 "프로브 상태-차이
(반사실 아티팩트)" vs "미러 무효"로 재프로브로 구분해 기록하고 **코드 제거 우선** → 화력은
[02-idle-bay](02-idle-bay.md)로.

## 기대 효과

* 26의 막힌 순간 5.97% 개봉 — 대기 → 즉시 배치 전환이라 tardiness 직접 절감. 전례 전환율의
  절반을 가정하면 **26 −3~8%(−0.3~0.8M)**.
* 부수: 타 문제도 같은 층을 2.4~3.4%(pre-N2 실측)씩 잃고 있어 광역 소폭 이득 가능. 정직 캡:
  거인 스필오버 기대는 낮다(38 crane ≤0.6% 실측).
* 안전 불변: 공식 체커 인증·repair 경로 무접촉.

## Results — 관문(미러 반사실) Kill: 빌드 전 계열 종결 (2026-07-17 밤, tools/ev01_crane_mirror.py)

미러**(변접촉 = 면적 0 = 합법, moving layer k vs fixed layer j≥k 쌍별 면적>EPS만 충돌)로
재판정했다. 데이터: reports/evidence_v3/ev01_prob_26.json.

* **미러 통과 0 / eaten 22 순간 (회수율 0.000, tardiness 가중 0.000)** — 거부 anchor 전수가
  체커 기준으로도 진짜 겹침. 분류 정합: band 2.1%(≈B20 재프로브 1.99%), eaten 6.6%(≈5.97%).
* **사인(D7 해상도): 전제 반증.** "게이트의 이중 보수(경계 양쪽 충돌)가 합법 배치를 잃게
  한다"는 가설이 죽었다 — crane-eaten 층은 수치-오차 거부가 아니라 **실제 반출-sweep 간섭**
  이다(변접촉 fuzz 관측은 쌍 단위 현상일 뿐, eaten 순간에서 전환되지 않음). 미러/미세기하
  회수 계열(N1→N2→B20→미러)은 26에서 **소진 선언**: 잔여 band 2%는 K-절단 바깥(K64 raw
  무효 실측), eaten ~6%는 진성 간섭.
* **부활 조건(사전등록)**: eaten 분류 자체가 바뀌는 계기 교정이 있을 때만(예: exit-시점
  잔차 기하의 반사실 오류 발견). 그 전 재시도 금지.
* **승계**: 26의 남은 실측 레버 = [03-thin-fragments](03-thin-fragments.md)의 두께-보존 항
  (26 캐너리 spread 양성 76~100%·총 regret 3199 실측) — 26은 하한 0 인증이므로 잔여 전액이
  파편화·모양 계열이라는 종전 판정과 정합. 본 이슈는 닫힌 질문.
