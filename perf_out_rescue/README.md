## #4 issue에 대한 해결책 — 배치 실패 block의 단독 배치로 인한 Z1 폭증

### 1. 제기된 문제사항

Phase 2에서 배치에 실패한 block은 **bay가 완전히 비는 미래 시점까지 밀린 뒤 단독으로 배치**된다(`forced`). 공간이 남아 있어도 부분 점유 상태에서 재시도하지 않으므로 EXIT가 due date보다 크게 늦어지고 Z1(총 tardiness)이 폭증한다.

#### 1.1 원인 (코드로 확정)

| 위치 | 무엇이 문제인가 |
|---|---|
| `Phase2/repair.py` `empty_bay_entry` | 강제 배치 시점을 "그 bay에 다른 block이 하나도 없는 첫 시점"까지 미룸 → 정의상 단독 배치 |
| `Phase2/repair.py` `force_place` | due date를 인자로 받지도 않음. 점수 없이 첫 orientation의 좌하단에 배치 |
| `Phase2/driver.py` crane 충돌 복구 안전망(Phase B) | 충돌 block 전부를 **재시도 없이 무조건** `force_place`. `info["forced"]`는 전부 여기서 생김 |
| `Phase2/driver.py` `_schedule_excluding` | 앞서 강제된 block의 시간 창이 다음 계산에 포함 → 강제 배치가 직렬로 이어지며 지연이 복리로 쌓임 |
| `Phase2/driver.py` `_earliest_slot` | 기존 block들 사이 빈 공간에서 가장 이른 배치 시점을 찾는 함수가 **이미 있으나**, 특정 portfolio 멤버의 구성 단계에만 연결되고 안전망(Phase B)에는 미연결 |

#### 1.2 실측 확증 (`tools/viz_diag.py` 진단 → `perf_out/diag/*/diag_blocks.json`)

| 문제 | 강제+단독 block이 Z1에서 차지하는 비율 | bay 점유율 <50%에서 강제됨 ("자리 있었음") | 강제 지연 중앙값 |
|---|---|---|---|
| prob_2 | **99%** | **16/19 (84%)** | 63일 |
| prob_27 | 100% | 23/81 (28%) | 707일 |
| prob_40 | 100% | 65/178 (37%) | **1,470일** (최대 3,316일) |

추가 확증 (40문제×180초 관측 캠페인, `perf_out/`): **ALNS 탐색으로도 이 병리는 안 풀린다** — 180초 후에도 forced가 prob_40 61→60, prob_38 41→45(오히려 증가). 구성 단계에서 안 고치면 끝까지 남는다.

> **핵심 판독**: 이슈 주장은 사실이며, 강제 배치는 두 부류로 갈린다 — (a) **자리가 있는데 정책 때문에 밀린 것**(끼워 넣기로 구조 가능), (b) **실제로 꽉 차서 밀린 것**(끼워 넣기로 못 풂). 본 해결책은 (a)를 공략한다.

### 2. 해결 방법 — 무엇을 / 어디를 / 왜 / 어떻게 바꿨나

> 아래는 통합 브랜치 `feat/integrated`에 적용된 형태다.

#### 2.1 핵심 변경 — 안전망(Phase B)에 "빈 공간 끼워 넣기" 삽입 (`Phase2/driver.py`)

**어디**: crane 충돌 복구 안전망의 충돌 block 처리 루프. **왜**: 충돌 block을 곧바로 빈 bay로 보내지 않고, 기존 block들 사이 빈 공간을 먼저 써서 지연을 줄이려고. **어떻게**:

```
충돌 block v (하루 미룰 때 지연 증가가 작은 것부터):
  1) 탐색 시도 상한이 남고 아직 시도 안 했으면 → _earliest_slot(v)로 빈 공간 탐색
  2) 자리 찾음 → 거기에 배치 (기록)
  3) 못 찾음, 또는 (끼워 넣었다가) 다시 충돌 → 원래 방식대로 force_place(빈 bay)
```

안전장치:
- 탐색 시도 상한 = **호출 횟수 기준** 16회/decode — 비용 상한 고정
- 끼워 넣었다가 재충돌한 block은 빈 bay로 되돌림 — 빈 bay는 어떤 검사에서도 충돌이 불가능하므로 이 되돌림이 **루프 종료를 보장** (스스로 감지해 복구하는 구조)
- 마지막 4번의 반복은 끼워 넣기 없이 순수 강제만 — 재인증 여유 확보
- 같은 block을 두 번 끼워 넣으려 하지 않음(무한 재시도 방지)

#### 2.2 배치 decode 안에 deadline 확인 지점 추가 (`Phase2/driver.py` + `Outer/realize.py`)

**왜**: 캠페인 채점에서 T=60 −1이 3건 나왔는데(§2.4), 원인은 **한 번의 배치 decode가 deadline을 넘겨도 끝까지 도는 것**이었다(예: 67.5초 반환). **어떻게**: `PlaceAndCrane`에 deadline을 전달해, 초과 시 남은 block들을 즉시 빈 bay 방식으로 마무리한다. deadline을 안 주면 아무 동작도 하지 않아 기존 경로 그대로다.

#### 2.3 설정 (`Phase2/config.py`)

```python
force_retry_phase_b: bool = True          # 안전망 끼워 넣기 — 채택(기본 ON)
force_retry_budget: int = 16              # 탐색 시도 상한 (튜닝 실험 진행 중)
force_retry_construction: bool = False    # 구성 단계 끼워 넣기 — 기각(기본 OFF, 선택)
force_retry_construction_budget: int = 32
```
**두 플래그 모두 False + baseline profile이면 원래 코드와 완전히 같은 해**를 낸다(아래 §2.5-1).

## #issue 7에 대한 해결책 — 배치 점수의 목적함수 정렬 (forced_risk)

### 1. 제기된 문제사항

배치 점수(contact 등)가 목적함수와 어긋난다 — 밀착(contact)을 키우면 먼저 나갈 block의 crane 경로를 막아 강제 배치를 유발할 수 있으므로, `forced_risk` 항을 강화하고 profile을 sweep해 default를 정하자는 제안. **구현·profile·sweep 스크립트는 PR #6으로 이미 main에 머지됐고, `forced_risk_20`이 default로 나가 있다**(§0-2에서 baseline으로 되돌림).

#### 1.1 주장별 실측 검증

| 이슈 주장 | 검증 결과 |
|---|---|
| "contact 중심 점수가 강제 배치의 원인" | **절반만 사실.** 강제 배치는 두 부류(§#4-1.2): 자리 있는데 밀린 것(prob_2류 84% — 점수와 무관, 끼워 넣기가 해결)과 실제 고밀도(prob_27류 ≥85% — 여기가 점수의 몫). 점수 개선 효과는 끼워 넣기가 걷어낸 뒤 남는 부분으로 재산정해야 함 |
| "forced는 안전망 도달 block 수" | **정확.** 단 구성 단계 강제는 원래 안 보였음 → #4에서 `forced_construction` 측정 필드로 봉합 |
| "`forced_risk_20`이 유망하나 단일 문제라 미확정" | **과소평가.** PR #6 sweep(20문제, 55초 관측)에서 **20문제 전승** — 단 아래 교란·부작용 있음(§3) |

### 2. 분석 · 반영 · 재설계

#### 2.1 forced_risk 구현 분석 (main `Phase2/scoring.py`)

**자기보다 먼저 나갈** resident에 대해 `긴급도(1/(1+EXIT차)) × [bbox 겹침 + crane 차단 여부]`, 상위 6개 resident만. 빠른 단계는 bbox 산술만(전 후보), 정밀 단계에서만 crane 질의(top-8×6 ≤ 48회, 캐시됨). **실측 비용 CPU 3.6%, 초당 반복 0.21→0.24(무손실)**. 기존 `premarsh` 항은 정확히 반대 방향(나보다 **늦게** 나갈 block)만 봐서 **중복 없음**을 코드로 확인.

#### 2.2 sweep 실측 (main `reports/scoring_sweep/`, 20문제×55초)

| 지표 | baseline | forced_risk_20 |
|---|---|---|
| objective | — | **20문제 전승, 2～5배↓** (prob_2: 7.7M→0.24M) |
| forced 평균 | 33.4 | **17.6** |
| 초당 반복 | 0.21 | 0.24 |
| **첫 실행가능해 최악** | 33.4초 | **43.3초** (prob_14 — 30초 시점 −1) |

단, 새 sweep 스크립트의 첫 실행은 **0건 성공**(시스템 Python에 shapely 없음), 5초짜리 설정은 첫 실행가능해(～6초)보다 짧아 **아무것도 측정 못 함** — 실험 인프라 결함 확인.

#### 2.3 통합본에 반영된 것

- **진입점 정리** (이슈 우선순위 1): `myalgorithm.py`의 deadline을 timelimit 기반 여유 공식으로(§0-1), scoring default를 `baseline`으로(§0-2), 환경변수 상한(§0-3)
- **측정 필드 봉합**: 끼워 넣기 성공/되돌림/구성 강제 수를 기록에 저장 (#4와 공유)
- **실험 방식 재설계**: (profile × deadline) 조합 반복 실행 폐기 — 측정 도구는 180초 관측 1회에서 모든 가상 timelimit의 품질을 후처리로 읽으므로 deadline 축 자체가 중복. 대신 층화 표본 + 제출 계약 채점 게이트

### 3. 채택 / 기각 근거 (전부 실측 기준)

| 항목 | 판정 | 실측 근거 |
|---|---|---|
| Feature A (먼저 나갈 block의 crane 차단 벌점) | **채택 — main 구현 유지** (정밀 단계, 상위 6개) | 강제 배치 메커니즘을 직격하는 유일하게 새로운 기하 신호(premarsh와 방향이 갈려 중복 없음). 포함 패키지가 20문제 전승, 비용 CPU 3.6%로 상한 |
| Feature B (bbox 겹침 벌점) | **채택 — 단 수정 2개 필요** (빠른 단계) | 독립 신호가 아니라 위험 후보를 정밀 단계로 올리는 선별기. 수정(§0-5·0-6): resident bbox 재사용, 디버그 카운터 게이트 |
| Feature C (여유 없는 block 가중 벌점) | **기각** | A의 긴급도 항과 같은 축의 변형이며 미구현·미측정. 현 실험 예산(1회 실행, 시드 미통제)으론 weight 1.0 vs 2.0조차 통계로 못 가름(중앙값 forced 11.5 동률) |
| Feature D (contact 축소 profile) | **기각** | 실측 열세: 55초 시점 개선율이 contact 절반 판 22.31% < baseline 28.9%. contact를 깎으면 뒤 block이 들어갈 자리가 나빠져 고밀도 강제를 되만듦 |
| `forced_risk_20`을 production default로 (main이 이미 출하) | **baseline로 되돌림, 다시 default로 올리는 것은 실험 후** | ① 전승이 끼워 넣기 **없이** 측정됨 — 같은 채널이라 효과 겹침 → 끼워 넣기 켠 위에서 2×2 실험 후 판단. ② 첫 실행가능해 33.4→**43.3초**로 짧은 T −1 위험. §0-2 |
| (profile × deadline) sweep 축 | **기각** | ① 180초 관측 1회로 전 가상 T를 읽음(축 중복). ② 55초 관측은 아직 개선 중인 11문제(최악 문제군)를 못 봄. ③ 실증: 5초 설정 측정 무의미, 새 sweep 0건 성공 |
| main의 deadline 여유 2.0초 | **기각 → 여유 공식 채택** | 2.0초 < 워커 회수 대기 8～25초 → 워커 지연 시 반환이 T 초과(구조적 −1). 실측 단일 반복 최악 46.9초도 여유를 압도 → 여유 12～30초로 반환<T를 수학·실측 이중 검증. §0-1 |
| 이슈 우선순위(scoring sweep을 2순위) | **4순위로 재조정** | 앞 순위가 더 싸고 검증됨: ① timelimit 준수(짧은 T 확정 −1 제거), ② 빈 공간 끼워 넣기(#4), ③ 추가 decode 승률 확인(§0-7). 점수 실험은 이들이 바꿀 기준선 위에서 해야 유효 |

**판단 원칙 (#4와 동일 + 교란 통제)**: 한 번에 한 요인만 — 점수 실험은 끼워 넣기 ON을 새 기준선으로, deadline·decode 수는 전 조건 고정, profile은 매 실행 명시, 관련 환경변수 해제. 근거: main `reports/scoring_sweep/`, 이 트리 `perf_out*/`.
