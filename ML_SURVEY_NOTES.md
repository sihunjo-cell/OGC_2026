# Broader ML survey notes for OGC solver integration

## Practical thesis

For this solver, ML should not replace the geometric feasibility engine or the
official checker. Those are hard constraints and already heavily optimized.
The useful role is to replace expensive or brittle *choices* around that engine:

1. Which solver arm/config should receive time?
2. Which released block should be admitted first within a bay?
3. Which candidate anchors/orientations deserve exact crane/space checks?
4. Which ALNS destroy/repair/restart move should be attempted now?

This matches the current literature trend: learned components are most reliable
when embedded inside strong classical search, not when used as end-to-end
solvers.

## Literature map

### Algorithm / configuration selection

Papers and surveys on algorithm selection and automated configuration support
the current first implementation:

- Kotthoff, "Algorithm Selection for Combinatorial Search Problems" (AI
  Magazine, 2014).
- Kerschke et al., "Automated Algorithm Selection: Survey and Perspectives"
  (Evolutionary Computation, 2019).
- Alissa, Sim, Hart, "Automated Algorithm Selection: from Feature-Based to
  Feature-Free Approaches" (Journal of Heuristics, 2023).
- Hydra and irace show that portfolios plus automated configuration are often
  stronger than one hand-picked solver.

OGC mapping:

```
prob_info features -> pf0/pf1/pf2/pf3/extended arm
```

Data cost is low because each label is just the best observed objective among
existing arms.

### Learned ALNS / LNS control

Relevant papers:

- Reijnen et al., DR-ALNS / Online Control of ALNS (ICAPS 2024).
- Hottung and Tierney, Neural Large Neighborhood Search (AIJ 2022).
- Wu et al., Learning LNS Policy for Integer Programming (NeurIPS 2021).
- Huang et al., CL-LNS with contrastive learning (ICML 2023).

OGC mapping:

```
search state -> destroy/repair/restart/operator scope
```

This can be powerful, but label/reward assignment is expensive. It requires
iteration-level logging and many counterfactual trials, or an offline RL setup.

### Dispatch priority learning

Relevant papers:

- GNN/RL priority dispatch rule generation for distributed job-shop scheduling
  (Journal of Manufacturing Systems, 2023).
- DRL scheduling papers in flexible/dynamic job shop settings.
- Imitation-learning dispatch papers combining classification/ranking.

OGC mapping:

```
released queue + bay state + current partial layout -> order hint / priority
```

This is probably the best second ML target because `Outer.inbay` already exposes
a safe hook: `dispatch_order_hint`. Labels can be generated by trying several
order hints and keeping the one with the best realized objective.

### Packing / nesting placement learning

Relevant papers:

- Transformer RL for online 2D strip packing (Computers & Industrial
  Engineering, 2025).
- Deep-Pack and later DRL approaches for 2D/3D online bin packing.
- "Nest smarter, not harder" for 2D irregular nesting with rotational placement
  (Journal of Intelligent Manufacturing, 2025/2026).
- DRL for irregular shape nesting in shipbuilding (2021).

OGC mapping:

```
candidate anchor/orientation features + local occupancy features -> score/rank
```

This has higher upside than config selection, but data extraction is heavier.
The safe way is a pairwise ranker, not a direct coordinate generator: keep the
current exact raster/crane checks, but rank the candidate cells before exact
evaluation.

### Surrogate-assisted expensive combinatorial optimization

Relevant papers:

- Surveys on surrogate-assisted evolutionary algorithms for expensive
  combinatorial optimization (2024+).
- Pairwise comparison surrogates for expensive multi-objective optimization.
- GBDT-based surrogate methods for permutation/combinatorial spaces.

OGC mapping:

```
cheap candidate/move features -> predicted improvement or pairwise winner
```

This is relevant because `realize()` is expensive. A surrogate could screen
ALNS/inbay/candidate alternatives before spending full Phase2 time. Pairwise
ranking is more plausible than objective regression.

## Current priority after the selector dataset

1. Finish arm-selection dataset and measure VBS/SBS gap:
   - If best-arm labels are nearly constant, discard selector.
   - If labels vary and oracle beats single-best, train a small classifier/ranker.

2. Add a `dispatch_order_hint` dataset:
   - features: queue block stats, bay density, tardiness contribution, area,
     preference loss, slack, current admitted count.
   - actions: current inbay modes (`tardy_first`, `least_slack`, `edd`,
     `large_first`, `late_entry_first`).
   - label: best realized mode by objective delta.

3. Add candidate anchor pairwise data only if dispatch-order data shows signal:
   - collect top cells from current `Raster.order_cells`;
   - label chosen admitted anchor vs rejected/unused top alternatives;
   - train a tiny GBDT/logistic pairwise ranker.

## Why not end-to-end neural placement first

End-to-end packing papers are interesting, especially for irregular nesting, but
our objective includes bay preference, temporal release/due dates, crane sweep,
multi-layer geometry, reactive repair, and official feasibility checking. A
direct neural coordinate policy would need huge environment interaction and
would still require exact post-checking. Ranking or selecting existing safe
decisions gives most of the benefit with much less data risk.
